## ReUI design rules (every UI edit, follow-ups included)

This project uses an existing design system: ReUI on shadcn/ui. Keep its look. Generic frontend advice (vary fonts or themes, gradients, page-load or staggered reveals, "2-3 intentional motions", Framer Motion) does not apply here, and other design skills lose where they disagree.

1. Use installed components first (`components/ui`, `components/reui`): tables `data-grid`, filtering `filters`, boards `kanban`, modals `Dialog` or `AlertDialog`, toasts `sonner`. Never set height, radius, padding, shadow or motion on them; use `size`, `variant`, `spacing`.
2. Color: semantic tokens. State: `<Badge variant="success-light">` from `@/components/reui/badge` at default size, or Alert variants. Raw palette only for categorical identity, with its `dark:` pair.
3. Spacing: `gap-*` on the parent: `gap-1` to `gap-2` in a row, `gap-3` to `gap-4` between groups, `gap-6` to `gap-8` between sections. Type: `text-sm` body, `text-xs` meta, nothing smaller; never resize FrameTitle or CardTitle.
4. Motion: installed parts already animate; never retime them. Yours: hover `transition-colors`; reveal `duration-200 ease-[cubic-bezier(0.22,1,0.36,1)]`; transform and opacity only; never `transition-all`, bounce, or a stagger on table rows or lists of 20+; at most 1 entrance per view; `MotionConfig reducedMotion="user"` plus `motion-reduce:`.
5. Every data region: empty state with an action, `Skeleton` loading, inline error with Retry.
6. Before UI code, write the plan from `.agents/skills/reui/SKILL.md` in your reply. Before you finish, run its self-check on the files you changed and fix every hit (2 rounds at most). Full rules: `.agents/skills/reui/SKILL.md`. If that folder is missing, call the `reui` MCP tool `get_agent_skill`.

Managed by the ReUI installer. Edits between the markers are replaced on the next run.

## Virtual office (`.agents/`) — read before you work

This repository runs a **single-agent multi-role office**: you work as one agent but
switch between *modes*, each with its own scope and rules. Read these before your first
edit, in order:

| File | What it gives you |
| :--- | :--- |
| `.agents/ONBOARDING.md` | start here in a fresh session: what to read, how to run the env |
| `.agents/MEMORY.md` | architecture, Decision Log, and the traps that are expensive to rediscover |
| `.agents/ROLES.md` | the modes (`backend`, `frontend`, `security`, `qa`, …) and what each owns |
| `.agents/PROTOCOL.md` | how to activate a mode, hand off, and verify |
| `.agents/TASKS.md` | what is in flight right now |
| `.agents/rooms/` | optional per-workstream notes for long-running work |
| `.agents/automation/` | the cron automation's registered prompt and trigger |

Open every reply that does work with a mode line, e.g. `[mode: backend] — …`, and never
edit outside your mode's `Owns` column without handing off first.

**Autopilot.** For a bounded work item, hand off to `autopilot` / `delivery-lead`: the mode
sequence runs internally and the owner receives a single *Delivery Report* instead of
per-step handoffs. The office never stops to ask — it either proceeds or aborts and
reports. Policy and the merge gate: `.agents/PROTOCOL.md`; flow summary:
`.agents/ONBOARDING.md` → *How the office delivers work*.

**Never edit inside the `nextjs-agent-rules` or `reui-agent-rules` markers above** — those
blocks are regenerated by tooling.

## Developer sub-agents (`.agents/agents/`)

Project-level OpenHands file-based agents. They are scanned at conversation start; use
a new conversation for changes to take effect. Delegate with the `task` tool.

| Agent | Owns | Never touches |
| :--- | :--- | :--- |
| `backend-developer` | `src/app/api/**`, `src/modules/**`, `src/server/auth/**` | db schema/migrations |
| `frontend-developer` | `src/app/**`, `src/components/**` (ReUI design system) | `src/components/reui/**` internals |
| `database-migration-engineer` | `src/server/db/schema/**`, `src/server/db/migrations/**`, `drizzle.config.ts` | service/route logic |
| `code-reviewer` | Read-only review of any change | writes anything |
| `qa-test-engineer` | `tests/**` | production source (except minimal bug fixes) |

Build/verify commands: `pnpm typecheck`, `pnpm lint`, `pnpm test`,
`pnpm test:integration` (needs a disposable `INTEGRATION_TEST_DATABASE_URL`),
`pnpm check:deploy-env` (validates the deploy env contract; CI runs it before `pnpm build`).

Integration test environment gotchas (learned the hard way):

- `pnpm test:integration` reads `INTEGRATION_TEST_DATABASE_URL`, **not** `DATABASE_URL`.
  With no database it fails loudly (all 21 subtests `cancelled`, exit non-zero) instead of
  skipping, so a broken integration suite cannot look green. Confirm `pass 21` / `fail 0` /
  `skipped 0` on a green run.
  `pnpm test:integration:optional` keeps the old skip-only behaviour.
- The two integration files migrate the same database and used to race on a fresh one
  (`Failed query: CREATE TABLE "account"`). They now migrate under a PostgreSQL advisory
  lock (`tests/integration/migrate-safely.ts`), so a plain `pnpm test:integration` works
  on an empty database. Pre-migrating is no longer required.
- The webhook scenarios sign payloads with a hardcoded key
  (`SB-Mid-server-test-integration-key-32chars`) while `BillingService` verifies with
  `MIDTRANS_SERVER_KEY`. Both must match or every webhook test fails with
  `WebhookValidationError: Invalid signature`.
- `INTEGRATION_TEST_DATABASE_URL` fails closed: the DB name must contain `test`,
  `disposable`, or `scratch`, and the host must be local/container.

Full local run:

```sh
export INTEGRATION_TEST_DATABASE_URL="postgresql://postgres:postgres@localhost:5432/saas_starterkit_test"
export MIDTRANS_SERVER_KEY="SB-Mid-server-test-integration-key-32chars"
pnpm test:integration
```

`pnpm build` needs the CI env vars present (`NEXT_PUBLIC_MIDTRANS_CLIENT_KEY`,
`MIDTRANS_SERVER_KEY`, `BETTER_AUTH_SECRET`, `DATABASE_URL`). `CRON_SECRET` is optional at
build time but, when set, must be at least 32 characters or the build fails.

Billing invariants worth knowing before touching pricing:

- `src/modules/billing/plans.ts` is the single source of truth for what a plan costs and
  which intervals it may be sold on (`getPlanAmount`, `isSupportedInterval`). Never
  recompute a charge inline; a lifetime period bought at the monthly price was a real
  escalation bug.
- Pricing UI reads `getPlanDisplay(plan, interval)` for the amount and suffix, so the
  landing page and the dashboard billing page cannot drift from the charged amount.
  Both the landing pricing section (`src/components/pricing-section.tsx`) and the
  billing page share it; add new pricing surfaces on top of it, not around it.
- Checkout rejects invalid plan/interval pairs with `CheckoutValidationError` → HTTP 400.
  `createCheckoutSession` also validates, so non-HTTP callers are covered too.

Operational invariants:

- `/api/billing/cron/sync-expired` fails closed: with no `CRON_SECRET` it returns HTTP
  500 and runs nothing, and it compares the bearer token in constant time. Never
  restore the old "only check when the secret happens to be set" behaviour.
- The deploy environment contract is checked by `pnpm check:deploy-env`
  (`scripts/check-deploy-env.mjs`) before the build, so a missing or weak key fails in CI
  instead of at the first webhook. `src/env.ts` validates the same keys, including
  `CRON_SECRET` (optional, min 32 chars when set). Add a new env var to the script's key
  lists or the anti-drift test in `tests/deploy-env-check.test.ts` will fail.
- Migrations are not applied by `pnpm build`. Run `pnpm db:migrate` against the target
  database as a release step; CI proves they apply to a clean database first.
- `trustedOrigins` in `src/server/auth/index.ts` is built from env only. Do not add a
  literal deployment hostname back to that list.
- Account deletion (`user.deleteUser`) is enabled and guarded by `beforeDelete`, which
  calls `findDeletionBlockers` (`src/modules/account/deletion-guard.ts`). `order.userId`
  and `subscription.userId` cascade on user delete, so without that guard a member who
  paid for a shared workspace's plan would silently delete the plan and its payment
  history out from under the other members. Keep the guard, and keep the cascade
  behaviour in mind before changing any `onDelete` on a billing foreign key.
- The guard keys on the **payer**, not on membership. `collectOrgMembershipFacts` also
  inspects organizations whose live plan the user pays for but no longer belongs to
  (`isMember: false`), because an owner can remove the payer and the cascade still follows
  `userId`. `deleteSoleMemberOrganizations` only ever removes organizations the user is
  still a member of, so it can never delete a payer-only workspace.
- Vercel rejects a deployment whose commit author is not a member of the Vercel team
  ("Git author must have access to the project"). The check fails with no build logs, so
  it looks like an infrastructure problem when the code is fine. Author commits as a
  team member before pushing a branch that must deploy.
- An organization whose only member is the deleting user is intentionally allowed to
  cascade away with the account: `beforeDelete` deletes it explicitly, because no
  foreign key links `user` to `organization` (only `member.userId` cascades). Without
  that step, deleting a sole member would strand an organization row with no members
  that still holds its unique slug. The guard only blocks while other members remain.
- The deletion guard has a self-serve escape route, and the Organizations page must keep
  it working: an owner blocked as a sole owner promotes another member to owner (or
  removes the other members), then deletes. `src/modules/organization/member-management.ts`
  mirrors better-auth's organization-plugin guards so the members grid only offers actions
  the server accepts (owner and admin may update/remove members; only an owner may grant
  the owner role; the last owner can never be demoted or removed). Keep that module in
  sync with the plugin's `member` permission rules rather than inventing UI-only rules.

UI invariants (ReUI):

- Every data region carries three states: empty (with one primary action), loading (a
  `Skeleton` shaped like the real layout, never a bare spinner) and error (inline `Alert`
  with Retry). A dropped state still typechecks, lints and builds, so
  `tests/data-region-states.test.ts` asserts the markers per region. If you refactor a
  region, keep its loading branch anchored on its own flag — a `/<Skeleton/` assertion
  passes on a sibling region's skeleton and hides the regression.
- `rg` is not installed in this sandbox. The ReUI self-checks in
  `.agents/skills/reui/rules/quality.md` use ripgrep; run them with `grep -nHE` instead.
  A missing `rg` prints nothing, which reads exactly like a clean check.

## OpenLynk domain notes (read before touching creator/store/analytics code)

OpenLynk is a link-in-bio + digital-product storefront built on this starter kit. The
platform half (auth, orgs, billing, Midtrans) is the template's; the product half lives in
three modules added on top.

- `src/modules/creator/` — profiles, links, public page assembly, entitlements.
  `service.ts` (profile + links), `products.ts` (products + assets), `entitlements.ts`
  (plan → limits), `types.ts` (`PublicProfile`, `PublicLink`, `PublicProduct`).
- `src/modules/store/` — checkout, free claims, webhook settlement, deliveries, sales.
- `src/modules/analytics/` — event ingestion (`recordEvent`) and the dashboard summary.

Plan ids and prices are load-bearing. `PRICING_PLANS` in `src/modules/billing/plans.ts`
and `src/modules/billing/types.ts` are referenced by id from checkout and the webhook, so
rename the *display* copy only. Free = 5 links / 1 product / no analytics; starter = 50 /
10 / basic; pro = unlimited / 100 / advanced + custom domain + branding removal.

Entitlements are enforced server-side (`getCreatorEntitlements`, `checkLimit`), never only
in the UI. A limit rejection is a 402; a validation failure is 400.

Storefront caching is tag-based and the invalidation is easy to forget:

- Public pages use `use cache` + `cacheLife("minutes")` in
  `src/components/storefront/queries.ts`.
- Tag names live in `src/lib/storefront-cache.ts`. **Use the helpers there, not string
  literals** — a tag only one side knows about is a silent cache miss.
- Every creator/product write, and every sale that moves a product's `salesCount` (free
  claim, webhook settlement, refund), must call `invalidateStorefront(username)`. The
  storefront renders "N sold" from that counter, so a sale changes the cached page too.
- `invalidateStorefront` swallows the "no request scope" invariant error on purpose: a
  script or test writing to the DB is not an error, and `cacheLife` is the backstop.

Two boundary rules that bit us and will bite again:

- A Server Component cannot pass an `onClick` to an anchor — React refuses to render it
  and the page 500s. Interactive storefront bits (`TrackedLink`, `ViewTracker`,
  `ProductViewTracker`, checkout form) are client components so the page itself stays
  server-rendered and cacheable.
- The events route (`/api/events/link`) is public, so it verifies a `targetId` belongs to
  the profile before counting it — for link clicks *and* product views. Anything countable
  needs the same ownership check.

Drizzle + postgres.js (`prepare: false`): never bind a JS `Date` through a raw `sql`
template — the driver cannot serialise it on a non-prepared statement and the query throws
at runtime. Use `gte(column, date)`. Column expressions inside `sql` are fine.

Local dev DB is `openlynk` (`openlynk_dev` was used for the E2E run). `src/server/db/index.ts`
defaults to `openlynk`, but a shell `DATABASE_URL` overrides it — pass it explicitly when
you mean a specific database.
